## high: Release children inherit unrelated host credentials

id: fnd_sig-feat-library-4445d2d730-d3e5_c992c47ede
category: security
confidence: high
triage: confirmed-bug
status: open
feature: Python source src (feat_library_4445d2d730)

evidence:
- src/clawpatch_supervise/clawpatch_release.py:152-184 (_release_clawpatch_env)
- src/clawpatch_supervise/runner.py:174-205 (CommandRunner.run)
- tests/test_runner.py:15-45 (test_process_group_uses_exact_sanitized_release_environment)

The release environment begins as a complete copy of os.environ and removes only database/reset credentials and supervisor policy variables. Common credentials such as GITHUB_TOKEN, AWS_SECRET_ACCESS_KEY, cloud-provider tokens, and SSH_AUTH_SOCK remain available to supervised children and any repository-controlled commands they launch. CommandRunner forwards the supplied mapping directly to subprocesses.

recommendation:
Construct child environments from a minimal operational allowlist. Require explicit opt-in for provider credentials and ensure repository validation or repair commands receive a separately stripped environment.

test analysis:
The environment test verifies removal of DATABASE_URL and a database-reset guard only; it does not seed or reject unrelated credential classes.

suggested regression test:
Seed representative GitHub, cloud, package-registry, and SSH credential variables, run a child through CommandRunner with the release environment, and assert that none are present unless explicitly authorized.

minimum fix scope:
Change _release_clawpatch_env and add environment-isolation coverage in tests/test_runner.py.

repro:
Set GITHUB_TOKEN to a sentinel value, call _release_clawpatch_env(), and run a child that prints whether GITHUB_TOKEN exists; the child receives it.

## high: Repository path can be retargeted after display or preflight, causing changes in a different repository

id: fnd_sig-feat-cli-command-5181306ec0-_5ff7b40b3c
category: concurrency
confidence: high
triage: confirmed-bug
status: open
feature: Python CLI command clawpatch-supervise (feat_cli-command_5181306ec0)

evidence:
- src/clawpatch_supervise/clawpatch_external.py:415-423 (main)
- src/clawpatch_supervise/clawpatch_external.py:434-460 (main)

The path is resolved only while constructing the banner, then recreated as an unresolved Path and passed separately through preflight, environment provisioning, and an apply-enabled sweep. If --repo is a symlink that is retargeted after the banner or preflight, the command can inspect one repository and subsequently modify, commit, or push another. This is a filesystem TOCTOU issue with potentially destructive consequences.

recommendation:
Resolve and validate the repository path exactly once, before starting work, and pass that canonical Path to every preflight, state, cleanup, validation, and sweep operation. Convert resolution failures into a controlled CLI error.

test analysis:
No tests are linked for this feature, and the supplied files contain no test proving path identity remains stable across preflight and execution.

suggested regression test:
Create repositories A and B plus a symlink initially targeting A. Use the injected preflight callback to retarget it to B, then assert the sweep still receives the canonical path for A.

minimum fix scope:
Update main to establish one canonical repo Path and consistently use it throughout the command.

repro:
Point --repo at a symlink to repository A. After ensure_repository_idle returns, retarget the symlink to repository B. The banner names A, while run_sweep receives the unresolved symlink and can operate on B with apply=True.

## medium: Cleanup treats live-reference inspection as successful on platforms without /proc

id: fnd_sig-feat-library-4445d2d730-0897_3ae816f4b2
category: data-loss
confidence: high
triage: confirmed-bug
status: open
feature: Python source src (feat_library_4445d2d730)

evidence:
- src/clawpatch_supervise/cleanup.py:115-137 (_path_has_live_reference)
- src/clawpatch_supervise/cleanup.py:198-219 (cleanup_owned_runs)
- tests/test_cleanup.py:155-180 (test_cleanup_preserves_stale_owned_directory_referenced_by_live_child)

On macOS and other POSIX systems without /proc, _path_has_live_reference unconditionally returns False. If the recorded supervisor PID has exited but a descendant still has the directory as its cwd or holds files beneath it, stale cleanup can remove that active directory. The removal-time recheck uses the same unsupported probe and therefore does not close the gap.

recommendation:
Implement a conservative platform-specific reference probe, such as scoped lsof inspection on Unix without /proc. If reference ownership cannot be proven, classify the directory as UNSAFE rather than deleting it.

test analysis:
The only orphan-child test is explicitly skipped unless /proc exists, leaving the fallback behavior untested.

suggested regression test:
Mock an unavailable /proc and the platform reference inspector; prove that a referenced directory is preserved and that an unavailable or inconclusive inspector fails closed.

minimum fix scope:
Update _path_has_live_reference and add non-/proc cleanup tests in tests/test_cleanup.py.

repro:
On a POSIX system without /proc, create a stale marked run directory, start a child with that directory as cwd, use a dead PID in the marker, and invoke cleanup_owned_runs(apply=True); cleanup attempts to remove the live directory.

## medium: Docker cleanup is not armed while container startup is in flight

id: fnd_sig-feat-library-4445d2d730-135c_e4ea36dea2
category: bug
confidence: high
triage: confirmed-bug
status: open
feature: Python source src (feat_library_4445d2d730)

evidence:
- src/clawpatch_supervise/validation_services.py:534-580 (_provision_postgres_test_environment)
- src/clawpatch_supervise/validation_services.py:625-634 (_provision_postgres_test_environment)
- tests/test_validation_services.py:84-113 (test_malformed_container_id_output_still_removes_exact_container_name)

The cleanup try/finally begins only after docker run has returned successfully. If startup times out or raises after the Docker daemon accepted the request, _checked raises before the cleanup block is entered, potentially leaving the named container running indefinitely. The exact randomized container name is already known and could be used for best-effort cleanup.

recommendation:
Arm cleanup before invoking docker run. Track whether startup was attempted and perform best-effort removal by the exact generated name for timeout, launch-error, nonzero-exit, and malformed-output paths while preserving the primary exception.

test analysis:
The malformed-ID test covers cleanup after docker run returns success; it does not exercise timeout, exception, or nonzero startup paths.

suggested regression test:
Make docker run raise TimeoutExpired after recording its --name argument and assert that docker rm -f is attempted for that exact name.

minimum fix scope:
Restructure _provision_postgres_test_environment startup cleanup and extend tests/test_validation_services.py.

repro:
Provide a run stub that raises subprocess.TimeoutExpired for docker run and records later calls. _provision_postgres_test_environment raises without issuing docker rm -f for the generated container name.

## medium: Downloaded release wheel is executed without artifact-integrity verification

id: fnd_sig-feat-config-cf96aef71d-614ad_2223de7625
category: security
confidence: high
triage: confirmed-bug
status: open
feature: Shell/workflow config install.sh (feat_config_cf96aef71d)

evidence:
- scripts/install.sh:4-5
- scripts/install.sh:71-72
- scripts/install.sh:87

The version constrains the artifact name but does not authenticate its contents. The installer downloads the wheel from the network, installs it, and executes its entry point without checking a pinned digest or signature. A replaced release asset or compromised delivery path therefore becomes code execution as the installer user.

recommendation:
Publish a SHA-256 digest for each supported wheel and verify the downloaded artifact before installation, or use pip hash-checking mode with a pinned artifact hash. Reject custom sources unless they have an explicitly supplied digest.

test analysis:
No tests are linked to the installer, and the current flow has no expected digest against which a tampered artifact could be tested.

suggested regression test:
Provide a wheel whose bytes do not match the configured digest and assert that installation stops before pip installation or entry-point execution.

minimum fix scope:
Add a release-specific digest, download the wheel to a temporary file, verify its SHA-256 value, and install only the verified file.

repro:
Serve a modified wheel at an overridden source URL or replace the bytes returned for the expected asset; the script accepts and executes it without detecting that its contents differ from the intended release.

## medium: Filesystem-controlled event fields allow terminal escape and output-spoofing injection

id: fnd_sig-feat-cli-command-5181306ec0-_84251f8fbb
category: security
confidence: high
triage: confirmed-bug
status: open
feature: Python CLI command clawpatch-supervise (feat_cli-command_5181306ec0)

evidence:
- src/clawpatch_supervise/clawpatch_external.py:103-139 (_render_inspection)
- src/clawpatch_supervise/clawpatch_external.py:193-196 (_render_event)
- src/clawpatch_supervise/clawpatch_external.py:279-280 (_render_event)

Finding titles, evidence paths, commands, recommendations, and generic details are printed without filtering control characters. Repository filenames can contain escape, carriage-return, and newline characters, so an untrusted repository can emit ANSI or OSC sequences, overwrite displayed status, forge COMPLETE/STOPPED lines, or trigger terminal features such as clipboard operations.

recommendation:
Centralize terminal-safe rendering for all externally derived event fields. Escape C0/C1 terminal controls and safely indent or annotate embedded line breaks while preserving newlines introduced by the renderer itself.

test analysis:
No linked tests were supplied, and there is no visible adversarial rendering coverage for control characters or hostile filenames.

suggested regression test:
Pass events containing ESC, BEL, carriage return, and embedded newlines in titles, paths, commands, and details; assert no raw terminal-control sequence or unindented forged status line reaches the rendered output.

minimum fix scope:
Add one terminal-sanitization helper and apply it to all event-derived values in _render_inspection and _render_event.

repro:
Render a finding whose evidence path contains an ESC-prefixed ANSI or OSC sequence, or a newline followed by a forged COMPLETE line. The raw control characters are returned and printed unchanged.

## medium: Fresh installs require a globally writable npm prefix

id: fnd_sig-feat-config-cf96aef71d-27cac_fc893f49e9
category: build-release
confidence: high
triage: risk
status: open
feature: Shell/workflow config install.sh (feat_config_cf96aef71d)

evidence:
- scripts/install.sh:52-66

When ClawPatch is absent, the installer uses `npm install --global`. On common system Node.js installations, the global prefix is owned by root, so an ordinary user cannot complete installation even though the script otherwise defaults to user-owned locations under `$HOME`. This also makes an installer run with elevated privileges modify system-wide state.

recommendation:
Install the pinned ClawPatch package under `install_root`, as is already done for ClawHub, validate its local executable, and link it into `bin_dir`.

test analysis:
No tests are linked to this feature, and this failure requires exercising the installer with a root-owned npm global prefix.

suggested regression test:
Run the installer with a fake npm whose global installation fails as unwritable but whose prefix-local installation succeeds, then assert that the resulting ClawPatch command is user-local and reports version 0.7.2.

minimum fix scope:
Change the ClawPatch installation branch in scripts/install.sh to use a prefix below install_root and update PATH or command resolution accordingly.

repro:
Run the installer as a non-root user with distro-provided npm, a root-owned global npm prefix, and no existing `clawpatch` command; npm exits with a permissions error.

## medium: KeyboardInterrupt reports that no source changed even after an apply-enabled sweep may have modified it

id: fnd_sig-feat-cli-command-5181306ec0-_06a2a45a04
category: api-contract
confidence: high
triage: contract-mismatch
status: open
feature: Python CLI command clawpatch-supervise (feat_cli-command_5181306ec0)

evidence:
- src/clawpatch_supervise/clawpatch_external.py:448-460 (main)
- src/clawpatch_supervise/clawpatch_external.py:486-492 (main)
- src/clawpatch_supervise/clawpatch_external.py:65-89 (_resolve_fresh_mode)

The sweep explicitly runs with apply=True and may already have changed or committed source before an interrupt occurs. The unconditional message that no source changed is therefore false. Its instruction to rerun for a fresh start is also inconsistent with the default mode, which retains or resumes non-clean state. This can mislead an operator about the repository and checkpoint state after interruption.

recommendation:
Use a state-neutral interruption message stating that applied source or checkpoint changes may remain and must be inspected. Give resume guidance consistent with the actual checkpoint outcome instead of promising a fresh start.

test analysis:
No linked CLI tests exercise an interrupt after an apply-enabled sweep has made changes.

suggested regression test:
Have an injected sweep create a tracked modification and raise KeyboardInterrupt; assert exit code 130 and verify the message neither denies possible changes nor promises an automatic fresh start.

minimum fix scope:
Correct the KeyboardInterrupt handler text and add one interrupted-after-mutation CLI test.

repro:
Inject a run_sweep implementation that modifies a temporary repository and then raises KeyboardInterrupt. main returns 130 while printing that no source changed and suggesting a fresh start.

## medium: Updating the live virtual environment can break a previously working installation

id: fnd_sig-feat-config-cf96aef71d-6e5c4_e059abb82c
category: data-loss
confidence: high
triage: confirmed-bug
status: open
feature: Shell/workflow config install.sh (feat_config_cf96aef71d)

evidence:
- scripts/install.sh:71-72
- scripts/install.sh:87-92

The installer creates or updates the fixed `install_root/venv` in place before validating the newly installed executable. On upgrades, the existing public symlink already points into that environment. If pip succeeds but the new command fails its version check, or the process is interrupted while files are being replaced, the installer exits while leaving the formerly working command altered or unusable.

recommendation:
Build and verify a staging virtual environment outside the live path, then atomically switch the public symlink or versioned installation pointer only after every validation passes. Preserve the previous environment for rollback until the switch succeeds.

test analysis:
No linked installer tests exercise failed upgrades or interruption while an existing installation is active.

suggested regression test:
Install a known-good fixture, attempt an upgrade using a fixture whose version command fails, and assert that the original linked command still executes and reports its original version.

minimum fix scope:
Stage the virtual environment at a unique sibling path, validate it there, and defer replacement of the active target until validation succeeds.

repro:
Install once, keep the public symlink, then rerun using a wheel whose installation succeeds but whose `clawpatch-supervise --version` exits nonzero. The installer aborts after replacing the package in the live environment, and the old linked command is no longer available.

## low: Package and CLI versions have independent sources of truth

Distribution metadata is versioned in pyproject.toml while the --version command reads a separate literal from __init__.py. They currently match, but either can be updated independently, allowing a published wheel and its executable to report different versions.

Assert that importlib.metadata.version('clawpatch-supervise'), clawpatch_supervise.__version__, and --version agree in an installed-package test.

minimum fix scope:
Consolidate version lookup in __init__.py or clawpatch_external.py and add one release-version consistency test.

repro:
Change only project.version, build/install the package, and compare package metadata with clawpatch-supervise --version.

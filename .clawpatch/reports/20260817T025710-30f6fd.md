## high: Escalated revalidation bypasses mutation-aware exception handling

id: fnd_sig-feat-library-2897a385df-bd67_64c75712f9
category: bug
confidence: high
triage: confirmed-bug
status: open
feature: Python source src/clawpatch_supervise/:validation (feat_library_2897a385df)

evidence:
- src/clawpatch_supervise/validation.py:485-518
- src/clawpatch_supervise/validation.py:519-561

Only the initial _revalidation_payload call is protected by the source-fingerprint exception handler. Workspace-write and host-bypass calls occur outside that try block. If either mutates source and then fails, its SafetyError escapes without the post-failure fingerprint check or the _UnresolvedFinding outcome used to preserve same-finding progress. The code also launches escalation before checking whether the initial call already changed source.

recommendation:
Check the fingerprint immediately after every revalidation call and place every escalation call inside the same mutation-aware exception handling path.

test analysis:
The included tests do not exercise _impl_revalidate or its escalation failures.

suggested regression test:
Simulate source mutation followed by failure during workspace-write and host escalation; require _UnresolvedFinding with the source-progress outcome and no subsequent revalidation call.

minimum fix scope:
Refactor _impl_revalidate so each attempt shares one guarded execution helper, then add escalation mutation/failure tests.

repro:
Stub the initial payload as open, then have the escalated payload modify a source file and raise SafetyError. The error escapes directly and lines 561-570 are never reached.

category: security

status: open

repro:

## medium: Checkpoint atomic writes do not durably persist the rename

id: fnd_sig-feat-library-e9500b5a4a-8e9d_b2319219e6
category: data-loss
confidence: high
triage: confirmed-bug
status: open
feature: Python source src/clawpatch_supervise (feat_library_e9500b5a4a)

evidence:
- src/clawpatch_supervise/checkpoint.py:10-31 (CheckpointStore)
- src/clawpatch_supervise/util.py:187-202 (atomic_write_text)

The implementation fsyncs the temporary file and replaces the destination, but never fsyncs the parent directory. On POSIX, a crash or power loss can therefore lose the directory entry update even though `CheckpointStore` promises durable supervisor state, leaving recovery without its latest progress or proof.

recommendation:
After `os.replace`, open the parent directory and fsync it on platforms that support directory descriptors; handle unsupported platforms explicitly.

test analysis:
The included tests cover cleanup and command execution, not crash durability or directory synchronization of checkpoint writes.

suggested regression test:
Mock descriptor operations and assert a successful atomic replacement fsyncs both the file and its parent directory.

minimum fix scope:
Harden `atomic_write_text`; all JSON checkpoint and proof writes then inherit the fix.

## medium: Explicit empty child environments inherit ambient secrets

id: fnd_sig-feat-library-e9500b5a4a-f8af_dc0379e0e7
category: security
confidence: high
triage: confirmed-bug
status: open
feature: Python source src/clawpatch_supervise (feat_library_e9500b5a4a)

evidence:
- src/clawpatch_supervise/queue.py:144-164 (_impl_fix_command)
- tests/test_runner.py:29-77 (CommandRunnerEnvironmentTests.test_process_group_uses_exact_sanitized_release_environment)

Using `env or dict(os.environ)` treats an explicitly supplied empty dictionary as absent. A caller requesting an empty environment therefore passes ambient credentials, database URLs, and dangerous feature flags to ClawPatch, contradicting the tested exact-environment isolation contract.

recommendation:
Use `env if env is not None else dict(os.environ)` so only omission enables ambient inheritance.

test analysis:
The environment isolation test supplies a nonempty sanitized mapping, so it does not exercise the falsey empty-mapping case.

suggested regression test:
Invoke the fix command with `env={}` under a patched ambient secret and assert `_run_clawpatch` receives exactly an empty mapping.

minimum fix scope:
Change the environment selection in `_impl_fix_command` and add one queue-level regression test.

repro:
Capture the environment passed to `_run_clawpatch`, set an ambient sentinel such as `GITHUB_TOKEN`, and invoke the fix path with `env={}`; the sentinel is forwarded.

## medium: Network artifact download has no time or size bound

id: fnd_sig-feat-config-cf96aef71d-99fa6_31f6df27d1
category: security
confidence: high
triage: confirmed-bug
status: open
feature: Shell/workflow config install.sh (feat_config_cf96aef71d)

evidence:
- scripts/install.sh:252-263

urlopen() is called without a timeout and copyfileobj() streams until EOF without limiting bytes. A stalled or slow source can hang installation indefinitely, while an oversized response can exhaust temporary-disk capacity before the SHA-256 mismatch is detected.

recommendation:
Apply explicit connection/read and total-operation deadlines, reject excessive Content-Length values, and copy through a bounded loop that aborts after a documented maximum artifact size.

test analysis:
No tests were included or linked for this feature, and ordinary successful-download tests would not exercise stalled or unbounded responses.

suggested regression test:
Use a local HTTP server to verify that a non-terminating response fails within the configured deadline and that a response exceeding the maximum artifact size is aborted and cleaned up.

minimum fix scope:
Update the Python download block in scripts/install.sh and add installer tests for timeout and size-limit failures.

repro:
Set CLAWPATCH_SUPERVISE_SOURCE to an HTTP server that accepts the connection but never completes its response, or continuously streams data, and provide any syntactically valid SHA-256 value.

minimum fix scope:
Update the event-rendering path in clawpatch_external.py and add focused regression tests for redaction across inspection and generic progress events.

repro:
Call display with a finding event whose reproduction contains a recognizable credential, or with a command event containing a credential-bearing URL, and observe that the value is printed unchanged.

## low: Legacy provider-failed outcome is misclassified as provider-refused

id: fnd_sig-feat-library-04c78af7f0-b5d8_7f4ee47f38
category: api-contract
confidence: high
triage: contract-mismatch
status: open
feature: Python source src/clawpatch_supervise/:clawpatch (feat_library_04c78af7f0)

evidence:
- src/clawpatch_supervise/clawpatch_protocol.py:42-50 (_EXIT_FAILURES)
- src/clawpatch_supervise/clawpatch_protocol.py:84-95 (failure_from_legacy_outcome)

The canonical exit mapping defines provider failure as exit 1 and provider refusal as exit 4, but the legacy outcome named revalidation-provider-failed is translated to exit 4. Consumers therefore receive PROVIDER_REFUSED and refusal-based reason text instead of PROVIDER_FAILED. Both kinds currently share transition flags, which masks the mismatch in behavioral tests but leaves reporting and future kind-specific logic incorrect.

recommendation:
Map revalidation-provider-failed to ("revalidation", 1), or rename the legacy outcome if it genuinely represents provider refusal.

test analysis:
No linked tests were included, and tests asserting only transient or progress-capable behavior would pass because both failure kinds currently have identical flags.

suggested regression test:
Assert that failure_from_legacy_outcome("revalidation-provider-failed").kind is ClawpatchFailureKind.PROVIDER_FAILED and that its transition reason starts with "provider-failed".

minimum fix scope:
Update the single legacy mapping and add a focused protocol regression test.

repro:
Call failure_from_legacy_outcome("revalidation-provider-failed") and observe that the returned kind is PROVIDER_REFUSED.
